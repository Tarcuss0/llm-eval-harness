# Проверка качества LLM-задач: пороги приёмки и поиск регрессий

Инструмент для одного вопроса: стало лучше или хуже после того, как я поправил промпт, сменил модель или переписал цепочку.

Прогоняет задачу по набору размеченных случаев, считает метрики, задержку и стоимость вызова, сравнивает с предыдущим прогоном и возвращает ненулевой код, если пороги не пройдены. Ставится шагом в CI.

## Зачем

Качество LLM-функциональности обычно оценивают просмотром нескольких ответов. Это работает до первого изменения, которое чинит один класс случаев и ломает другой.

Главная проблема — среднее по набору. Оно спокойно остаётся прежним, когда половина случаев улучшилась, а половина сломалась. Поэтому тут сравниваются не только средние, но и каждый случай отдельно: что починилось, что сломалось, где появилась ошибка.

Пример из поставки, которая лежит в репозитории. Вторая версия разбора писем выглядит лучше по всем сводным цифрам:

```
fields_match       0.778  →  0.878   ↑ 0.100
pass_rate          0.700  →  0.800   ↑ 0.100
items_overlap      0.900  →  0.887   ↓ 0.013

Сломалось (2):
  - long-names  fields_match: 1.00 → 0.78
  - long-names  items_overlap: 1.00 → 0.20
Починилось (4):
  - after-total  fields_match: 0.67 → 1.00
  - after-total  items_overlap: 0.67 → 1.00
  - fractional-qty  fields_match: 0.11 → 1.00
  - fractional-qty  items_overlap: 0.67 → 1.00
```

Средние выросли, но длинные названия товаров перестали извлекаться целиком. По сводке этого не видно, по списку случаев видно сразу.

## Как устроено

**Задача** — обычная функция: получает случай, возвращает ответ и расход токенов. Что внутри, инструмент не знает: один вызов модели, цепочка, агент с инструментами.

```python
from evalkit.core import Case, Prediction

def run(case: Case) -> Prediction:
    answer = my_pipeline(case.input)
    return Prediction(
        output=answer.text,
        model="gpt-4o-mini",
        input_tokens=answer.usage.prompt_tokens,
        output_tokens=answer.usage.completion_tokens,
    )
```

**Набор** — jsonl, строка на случай. Обязательны `id` и `input`, остальное читают метрики.

```json
{"id": "after-total", "tags": ["структура"], "input": "Блок внутренний 6 шт\nИтого по этажу.\nПульт 6 шт", "expected": {"items": [{"name": "Блок внутренний", "qty": 6, "unit": "шт"}, {"name": "Пульт", "qty": 6, "unit": "шт"}]}}
```

**Конфиг** связывает всё вместе и задаёт пороги приёмки.

```yaml
name: extract_items
task: examples.extract_items.task:run
dataset: dataset.jsonl
repeats: 1

metrics:
  - type: json_valid
  - type: set_overlap
    field: items
    name: items_overlap
  - type: fields_match
    field: items
    fields: [name, qty, unit]

thresholds:
  json_valid: 1.0
  items_overlap: 0.9
  p95_latency_ms: 3000
  cost_per_case_usd: 0.01
  errors: 0

pricing:
  gpt-4o-mini: {input: 0.15, output: 0.60}
```

Для задержки, стоимости и ошибок порог означает «не выше». Для остальных величин — «не ниже». Цены задаются в долларах за миллион токенов, стоимость считается по токенам, которые вернула сама задача.

## Запуск

```bash
pip install -r requirements.txt
```

```bash
# прогон, сохранение результата
python -m evalkit run examples/extract_items/config.yaml --save runs/base.json

# новый прогон со сравнением
python -m evalkit run examples/extract_items/config.yaml --baseline runs/base.json

# сравнение двух сохранённых прогонов
python -m evalkit compare runs/base.json runs/new.json

# какие метрики есть
python -m evalkit metrics
```

Пример в репозитории работает без ключей: вместо модели подставляется разбор на регулярных выражениях, который ведёт себя как модель и на части писем ошибается. Переменная `EXTRACT_VARIANT=v2` переключает вторую версию — на ней и видно разбор выше. Настоящий вызов включается переменной `LLM_API_KEY`.

## Метрики

| Метрика | Что проверяет |
|---|---|
| `json_valid` | ответ разбирается как json, в том числе обёрнутый в тройные кавычки |
| `exact_match` | полное совпадение; по умолчанию без учёта регистра, лишних пробелов и разницы `е`/`ё` |
| `contains` | ответ содержит подстроку из конфига или из эталона |
| `regex` | ответ соответствует выражению |
| `fields_match` | доля совпавших полей; для списков сопоставляет по порядку и штрафует разницу в длине |
| `numeric_close` | числовое поле в пределах допуска, абсолютного или относительного |
| `set_overlap` | пересечение множеств по мере Жаккара |

Своя метрика добавляется декоратором:

```python
from evalkit.metrics import register

@register("ends_with_question")
def ends_with_question():
    def metric(output, expected):
        return 1.0 if str(output).rstrip().endswith("?") else 0.0
    return metric
```

## Повторы и устойчивость

При ненулевой температуре модель отвечает по-разному на один и тот же вход. `repeats: 5` прогоняет каждый случай пять раз: оценка берётся средняя, а `stability` показывает долю самого частого ответа. Единица — ответы совпали, 0.4 — модель плавает, и к такой функциональности нельзя привязывать бизнес-логику без проверки.

## В CI

```yaml
- run: python -m evalkit run evals/config.yaml --baseline evals/baseline.json --fail-on-regression
```

Код возврата отличен от нуля, если не пройден порог или сломался хотя бы один случай. Базовый прогон держится в репозитории рядом с набором и обновляется осознанно, когда изменение признано улучшением.

## Что считается ошибкой, а что результатом

Падение задачи на случае не роняет прогон: случай помечается ошибкой, попадает в счётчик `errors` и в сравнение как новая поломка. Так видно разницу между «модель ответила плохо» и «вызов не прошёл вовсе».

## Чем собиралось

Python, pyyaml, httpx для примера с реальным вызовом. Тесты на pytest, 53 штуки, проверены внесением ошибок в код — каждая внесённая поломка роняет тесты.
